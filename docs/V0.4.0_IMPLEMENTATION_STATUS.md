# RFScout v0.4.0 implementation status

This document records which v0.4.0 roadmap foundations are already present on `main` and identifies the implementation slice carried by the current WiFi/BLE dynamic-retention work. `ROADMAP.md` remains the canonical release scope and `V0.4.0_PLAN.md` remains the detailed checklist.

## Verified on current main

The implementation history and production documentation show that several v0.4.0 foundations have already landed, even though the milestone remains incomplete:

- **Owner-aware PSRAM memory manager — implemented by PR #63.** Application and operation ownership, PSRAM-only managed allocation/growth, accounting, failure tracking, and bulk reclamation are present in `memory_manager.c/.h` and documented in `MEMORY_MANAGEMENT.md`.
- **Transactional application lifecycle — implemented by PR #64.** App transitions use Prepare / Reachability / Commit / Reclaim ordering, abort before reclamation when the source cannot be made safe, and reclaim managed app memory only after collector/worker reachability is cleared.
- **Independent visual theme and audio policy — implemented by PR #60.** Indoor/Outdoor/Night presentation and Normal/Quiet audio policy are separate persisted settings; release-level validation items remain outstanding.
- **Shared system events and Recent Events UI — implemented by PRs #61 and #65.** The semantic event/history/presentation boundary, initial hardware events, attention wake, and optional System Events app are present; broader hardware-event coverage and device validation remain outstanding.

The published v0.3.2 release was cut from a commit after these infrastructure PRs merged, so these foundations are present in that firmware even though they are primarily groundwork for the v0.4.0 roadmap. The v0.3.2 release notes describe the release as including application stability and system-events work; git history is the authoritative confirmation for the owner-aware memory manager and transactional lifecycle changes.

## Current implementation slice

The next coherent roadmap dependency is the beginning of **Milestone 3 / Workstream C: dynamic WiFi/BLE retention and observation state**. This change intentionally implements the storage/lifecycle foundation before changing retention semantics or the identity model.

Implemented by this change:

- replace the boot-time fixed 1000-entry Wi-Fi/BLE observation allocation with a small lazy allocation that grows geometrically as observations arrive;
- allocate that retained observation payload through the owner-aware memory manager as `RFSCOUT_APP_WIFI_BT` memory;
- let the existing transactional lifecycle reclaim the entire observation collection after both Wi-Fi and BLE collectors have stopped and passed the reachability gate;
- preserve the long-lived observation-store mutex/callback registration while safely invalidating the cached app-owned pointer after lifecycle reclamation;
- preserve the existing finite Wi-Fi/BLE timeout semantics and source-independent aging while removing the fixed storage ceiling from the retained collection itself;
- keep the existing 1000-entry UI snapshot working limit for current rendering scratch paths; this is no longer the retained-store capacity.

## Still outstanding after this change

This is deliberately not the complete WiFi/BLE redesign. The following remain roadmap work:

- rename the user-facing WiFi / BT application to WiFi / BLE across UI and production documentation;
- migrate the separate surveillance-history store to growable app-owned memory;
- add Instant / Timed / Never retention semantics and active/stale UI behavior;
- add explicit memory-pressure eviction/degradation policy beyond preserving the current collection when growth fails;
- replace MAC-address-equals-device semantics with internal entity IDs, observed identities, confidence, and provenance;
- parse richer 802.11 roles/subtypes/association evidence and add AP/client/probe/SSID relationships;
- add Combined/Wi-Fi/BLE and radio-specific analytical views plus stable relationship drill-down;
- perform hardware stress validation for repeated app exit/re-entry, low-memory growth failure, and collector/reclamation races.

Keeping these boundaries explicit prevents the storage migration from silently claiming semantic behavior that has not landed yet.
