# CC1101

CC1101 is RFScout's receive-only Sub-GHz application. Shared SPI, lifecycle, memory, and application-transition contracts are defined in [Platform architecture](../ARCHITECTURE.md). The implementation intentionally separates radio acquisition from signal interpretation so protocol decoding, analysis, and UI presentation do not depend on ESP-IDF/RMT ownership details.

## Direction

The CC1101 application is being rebuilt around two complementary acquisition roles:

- **Discovery scan** — find active frequencies/channels and measure received activity.
- **Fixed-frequency receive** — tune to a selected frequency, demodulate the received signal, capture its native high/low timing stream, and attempt onboard analysis/decoding.

The existing sweep/spectrum implementation is not an architectural foundation that must be preserved. Useful low-level radio code may be retained, but the application should be organized around the abstractions below.

RFScout remains receive-only. Protocol recognition and decoding describe observed signals; they do not imply transmit/replay support.

## Layering

The intended data flow is:

```text
CC1101 radio
    |
    | asynchronous demodulated receive
    v
ESP32-S3 RMT capture provider
    |
    v
bounded DMA capture pool
    |
    | immutable/const completed capture
    v
capture coordinator
    |
    +--> signal analyzer / timing histogram
    +--> generic slicers
    |       +--> PWM / PPM / Manchester / related line coding
    |
    +--> protocol decoder registry
    |
    +--> compact decoded/analysis result models
             |
             v
             UI viewers
```

The layers have intentionally narrow responsibilities:

### CC1101 radio service

The radio service owns hardware-specific CC1101 behavior:

- SPI/register access;
- RF-path switching;
- frequency tuning;
- receive presets/modulation/filter configuration;
- GDO configuration for asynchronous demodulated receive;
- radio power/start/stop behavior; and
- RSSI sampling needed by discovery or receive metadata.

It does not know protocol names, decoder state, UI views, or retained application history.

### Capture provider

The capture provider owns ESP32-S3 RMT/GDMA interaction. It converts a tuned CC1101 GDO signal into bounded capture objects without interpreting protocol semantics.

RMT implementation details do not leak into decoders or UI code. The provider may receive hardware data in whatever chunks ESP-IDF requires internally, but the public capture contract is a completed bounded object, not an unbounded stream.

### Capture coordinator

The coordinator owns capture orchestration above the hardware boundary:

- obtain a completed capture from the pool;
- expose it read-only to analysis and decoder stages;
- collect compact derived results;
- update UI-facing models/history as appropriate; and
- release the raw capture back to the pool when no consumer may reference it.

The coordinator does not own the DMA allocation directly. It receives a lease on a completed pool entry.

### Analyzer, slicers, and protocol decoders

Consumers operate on an immutable completed capture.

The analyzer may derive timing distributions, repeated-frame structure, symbol-period estimates, likely line coding, and other descriptive signal characteristics.

Generic slicers convert raw level/duration observations into compact bit representations where useful. PWM, PPM, Manchester, differential Manchester, PCM/NRZ, or other reusable line-code handling belongs here rather than being reimplemented independently in every protocol decoder.

Protocol decoders consume either:

- a compact slicer/bit representation; or
- the original raw capture when the protocol cannot be represented cleanly by a generic slicer.

Decoders must not retain raw-capture pointers after their invocation returns. Decoder-private state should remain small and bounded; the raw waveform is not duplicated per decoder.

## Native timing representation

RFScout preserves the ESP32-S3 RMT receive semantics rather than normalizing or combining captured runs.

A native RMT symbol is a 32-bit value containing two timed levels:

```text
31             16 15              0
+----------------+----------------+
| level1 | dur1  | level0 | dur0  |
| 1 bit  |15 bit | 1 bit  |15 bit |
+----------------+----------------+
```

The canonical raw capture therefore stores RMT-compatible 32-bit symbol words. RFScout does not merge adjacent equal levels, synthesize wider timing fields, or otherwise rewrite the evidence before decoding.

Capture metadata records the timing resolution so consumers can convert ticks to human-readable time without altering the stored measurement. The RMT clock/resolution must be chosen from supported-protocol timing requirements rather than assuming that 1 us resolution is always preferable.

## Bounded capture pool

Raw acquisition uses a small fixed pool rather than dynamically growing or exposing streaming semantics to the rest of the application.

The initial target is:

- **2 capture buffers**;
- **2048 RMT symbols per buffer**;
- **8 KiB per buffer**;
- internal DMA-capable RAM.

A 2048-symbol buffer can represent up to 4096 individual timed levels. Normal remote-control packets are expected to use only a fraction of that capacity, while the hard bound keeps acquisition, decoder, and UI behavior deterministic.

The pool owns the underlying allocations. Users of the pool hold state/leases, not ownership of the memory.

Each entry follows an explicit state machine:

```text
FREE -> FILLING -> READY -> PROCESSING -> FREE
```

Semantics:

- **FREE** — available for the capture provider to arm for DMA;
- **FILLING** — exclusively owned by the hardware acquisition path;
- **READY** — complete and immutable, awaiting coordinator processing;
- **PROCESSING** — borrowed read-only by the coordinator/analyzers/decoders.

The RMT provider must never overwrite a buffer that is not `FREE`. The coordinator must never mutate a completed buffer.

If both buffers are unavailable when a new capture must start, RFScout records a capture overrun rather than silently overwriting evidence or introducing unbounded allocation.

## Capture completion

A capture is deliberately finite. It ends for one of these reasons:

- **Idle/end-of-transmission** — the received level remains inactive long enough to satisfy the configured end condition;
- **Capacity-limited** — the fixed capture buffer fills before the hardware stop condition. ESP-IDF keeps receiving until the stop signal while discarding excess symbols; the final bounded capture is explicitly marked truncated;
- **Abort/lifecycle** — tuning, mode, application, or service state changes invalidate the active acquisition.

A capture object should retain enough metadata to interpret its symbols without consulting mutable global radio state, including at least:

- tuned frequency;
- RMT timing resolution;
- radio receive preset/modulation;
- symbol count;
- completion reason / truncation state;
- useful RSSI metadata; and
- capture sequence/timestamp information where useful.

Long packets may span internal RMT/DMA blocks, but that hardware transfer behavior remains inside the capture provider. Above that boundary a capture has a known finite symbol count.

## Zero-copy decode path

The normal path does not copy the raw capture after RMT completion.

```text
DMA writes pool entry
        |
        v
     READY
        |
        v
 coordinator acquires const lease
        |
        +--> analyzer reads same memory
        +--> slicers read same memory
        +--> protocol decoders read same memory
        |
        v
 compact results retained
        |
        v
 pool entry released to FREE
```

A generic slicer may create a much smaller derived bit buffer as scratch/output. That is not a duplicate raw capture and should be bounded according to decoder needs.

Raw timing data is copied into ordinary application-owned PSRAM only when a feature genuinely requires retention after the pool entry must be recycled, for example an explicit waveform snapshot/raw viewer. Histograms, decoded protocol fields, timing statistics, and other compact results should be retained instead of pinning DMA buffers.

## Protocol framework

The decoder framework is registry-based and hardware-agnostic.

An initial implementation may invoke decoders sequentially; parallel decoder tasks are not required. Protocol decoders should be inexpensive state machines operating against one immutable capture and bounded scratch state.

The framework should support:

- raw-capture decoders;
- reusable slicer-driven decoders;
- multiple plausible matches where evidence is ambiguous;
- explicit no-match/invalid outcomes; and
- compact decoded result objects that remain valid after the raw pool buffer is released.

The first protocols should favor simple, easily testable receive-only remotes before expanding into more complex rolling-code families.

## Discovery and viewers

Discovery/scanning is a peer of fixed-frequency capture, not the core data model.

A discovery view may continue to sweep frequencies or may evolve into a channel/frequency activity histogram. Its job is to help the user select an interesting frequency and enter receive mode.

Once receiving at a fixed frequency, acquisition continues independently of presentation. UI viewer selection should not change the underlying decoder/capture architecture.

Useful receive viewers include:

- **Decoded** — recognized protocol and compact decoded fields;
- **Timing histogram** — mark/space/symbol-duration distributions;
- **Waveform** — raw level/duration snapshot when explicitly retained;
- **Activity** — frequency/RSSI or other descriptive signal activity.

A long center-button action is a candidate viewer-toggle gesture; the exact interaction may evolve with the implementation.

## Memory and lifecycle

The architecture follows RFScout's existing resource-session model.

- CC1101/RMT resources are platform/service-facing and must quiesce before application-owned state can be reclaimed.
- The fixed two-entry DMA capture pool is small enough to remain in internal DMA-capable RAM and is managed by the capture provider rather than the general retained-history allocator.
- Completed decoded/analysis models that must outlive a pool lease are application-owned.
- Large retained application data belongs in app-session PSRAM.
- Decoder stacks must not absorb large raw or bit-buffer copies.
- Leaving CC1101 must stop acquisition and prove callbacks/workers can no longer reference app-owned state before reclamation.

The capture pool may be allocated when the service is activated and released after the service is safely stopped; it does not need to survive unrelated application sessions.

## Failure behavior

Failure should remain explicit and bounded:

- DMA/capture allocation failure prevents receive capture from starting and is surfaced diagnostically;
- decoder failure or no-match does not invalidate the raw observation;
- a capture whose destination saturated before the stop signal is marked truncated;
- no free pool entry increments an overrun diagnostic rather than overwriting an in-use capture;
- optional retained-history/snapshot allocation failure must not corrupt the acquisition pool; and
- service shutdown must not reclaim buffers while RMT/DMA can still reference them.

## Validation targets

Hardware validation should include at least:

- discovery across supported CC1101 frequency bands;
- locking onto a known remote frequency;
- repeated capture of a simple OOK remote such as a garage-door/key-fob-style transmitter;
- long/repeated transmissions approaching multiple RMT hardware blocks;
- capture-buffer boundary/truncation behavior;
- deliberate A/B pool pressure/overrun behavior;
- timing histogram consistency for repeated transmissions;
- protocol decode consistency;
- rapid receive/discovery/viewer changes;
- repeated CC1101 -> Home -> CC1101 transitions;
- zero outstanding app allocations after exit; and
- stable PSRAM/largest-free-block behavior across repeated sessions.

## Current implementation transition

The branch may temporarily contain pieces of the earlier sweep classifier/history implementation while this architecture is built. Those structures are not compatibility requirements. The rework should preserve useful hardware/platform code where appropriate while replacing app-specific scaffolding that conflicts with the bounded capture/decode model above.
