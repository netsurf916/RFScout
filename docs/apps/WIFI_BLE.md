# WiFi / BLE

The WiFi/BLE application is RFScout's passive Wi-Fi and BLE observation surface. Platform lifecycle, memory, and collector ownership are defined in [Platform architecture](../ARCHITECTURE.md); future semantic-entity/topology work belongs in [ROADMAP.md](../ROADMAP.md).

> **Current naming:** the application descriptor and some Device Settings labels still use the older **WiFi / BT** name, while the monitor UI uses **WIFI / BLE**. The roadmap tracks completing that rename.

## Services and lifecycle

The application requires delayed activation and declares both the Wi-Fi monitor and BLE monitor session services. Both collectors must quiesce before app-session PSRAM can be reclaimed.

The normalized live observation store grows in app-owned PSRAM instead of enforcing the former fixed 1000-item limit. Collector ingestion uses an identity index rather than linearly rescanning the entire collection for every callback.

## Current presentation

The primary display shows:

- total retained observation count;
- Wi-Fi and BLE source counts;
- most common known vendors;
- unresolved globally administered addresses as **UNKNOWN**;
- locally administered/private/randomized addresses as **RANDOM**; and
- currently active surveillance signatures/counts.

Both the ordinary summary and surveillance presentation are projections of the same canonical active observation collection.

The current primary count is still based on canonical observation/address records. It is **not yet** the semantic physical-entity model planned for v0.4.0.

## Retention

Wi-Fi and BLE membership age independently.

Current settings are finite timeouts from **10–300 seconds** in 10-second steps, defaulting to **60 seconds** for each source. A record can therefore retain one source while the other source has already aged out.

Surveillance classification is an attribute of that canonical active record and expires with it; there is no independent surveillance-retention list.

WiFi/BLE persists a non-default threshold as the sparse `evidence_threshold` app setting (`probable` or `distinctive`). The retired pre-1.0 `surveillance_sensitivity` setting is not migrated; if encountered, it is ignored and pruned through the normal configuration-save workflow.

Instant / Timed / Never retention modes are not implemented yet.

## Vendor identity

RFScout resolves globally administered Wi-Fi/BLE MAC addresses against IEEE Registration Authority data generated by `tools/update_oui.py`:

| Registry | Prefix |
| --- | ---: |
| MA-L / OUI | 24 bits |
| MA-M | 28 bits |
| MA-S / OUI-36 | 36 bits |
| Legacy IAB | 36 bits |

Runtime lookup uses longest-prefix precedence: 36-bit, then 28-bit, then 24-bit. Current MA-S data wins an exact 36-bit collision with legacy IAB.

CID is not used for ordinary vendor attribution because CID assignments are not globally unique MAC-address allocations. IEEE attribution is skipped for multicast and locally administered addresses.

## Surveillance evidence

`data/surveillance_signatures.csv` is RFScout-curated metadata and is distinct from IEEE ownership data. Curated prefixes can therefore contribute surveillance evidence even when they are not IEEE vendor assignments.

The classifier combines prefix evidence with independent signals such as advertised BLE names, manufacturer/company identifiers, service UUID patterns, Remote ID evidence, and supported protocol evidence.

The **Evidence Threshold** setting selects the minimum evidence strength for a single observation and is presented directly as **Possible / Probable / Distinctive** rather than the former inverted High / Medium / Low sensitivity terminology. Evidence source and evidence strength are separate concepts: the evidence bitmask records what was observed (for example name, curated prefix/OUI, company identifier, service UUID, or protocol evidence), while strength expresses how specifically that observation supports a surveillance signature.

The threshold contract is:

- **Possible** — detection recall is favored and false positives are explicitly possible; researched signals should still have a reasonable basis for association rather than being generic radio activity.
- **Probable** — a surfaced detection should have strong product/family association and false positives should be unlikely.
- **Distinctive** — a surfaced detection should rely on evidence intended to be uniquely identifying under the supported passive-observation model.

**Possible** is the compiled default. These labels describe evidence quality rather than a numeric probability calculation. RFScout does not accumulate repeated weak observations into confidence: repeated observations refresh active presence, while a candidate retains the strongest qualifying evidence observed for that signature. An active record keeps its first qualifying surveillance signature until expiry.

Detection rules may assign different strengths to the same evidence source. For example, one known proprietary service UUID may be only possible evidence, while a validated combination of multiple services may be probable or distinctive. Conversely, a generic standard service UUID should not become surveillance evidence merely because the Possible threshold accepts weaker researched associations.

## Notifications

Ordinary Wi-Fi/BLE discovery feedback can be enabled independently from surveillance alerts. Surveillance notifications use semantic categories such as ALPR, body camera, drone, camera, smart glasses, and acoustic sensor where supported by the current signature table.

## Generated-data maintenance

Refresh generated IEEE and curated signature tables through their generators, never by editing generated `.inc` files directly:

```sh
python3 tools/update_oui.py
python3 tools/update_surveillance.py
python3 -m unittest discover -s tests -p 'test_*.py'
```

Relevant generated tables live under `main/services/wireless/`. Registry, generator, workflow, and generator-test changes should stay synchronized.

## Current limitations

Current production behavior does not yet provide semantic physical entities, Wi-Fi AP/client topology, probe relationships, stable relationship drill-down, BLE-native deep views, or conservative address-rotation correlation. Randomized addresses therefore remain evidence rather than proof of physical identity.
