# RFScout v0.4.0 implementation plan

This document is the detailed implementation checklist for the v0.4.0 roadmap milestone. It is intentionally forward-looking. Nothing here should be read as implemented behavior until the corresponding code is merged and the production documentation is updated.

The canonical release scope and rationale remain in [ROADMAP.md](ROADMAP.md). This file exists to keep the implementation sequence, ownership rules, and validation checklist together instead of spreading v0.4.0 planning across production documents.

## Release objective

Make RFScout applications behave like isolated consumers of a common pool of dynamic memory:

- long-lived platform services keep only the memory they genuinely need across applications;
- the active application may dynamically consume available PSRAM for retained observations, history, captures, and scratch processing;
- application exit first quiesces hardware/workers, proves that no execution context can still reference app-owned state, and only then releases all app-owned dynamic memory;
- the next application starts from a predictable memory baseline and can reuse the released PSRAM;
- PSRAM is a platform requirement for supported RFScout hardware targets.

This is resource isolation by lifecycle, not a promise that literally every byte of physical PSRAM is available to an application. Platform, RTOS, display, driver, DMA, and service allocations that must remain resident are excluded from the app-owned pool. Internal SRAM remains reserved for the system, stacks, latency-sensitive state, and allocations constrained by ESP-IDF or peripheral hardware; it is not treated as a substitute for PSRAM-capacity application storage.

## Workstream A: memory manager

### Ownership model

Define allocation ownership at minimum as:

- **Platform/service** — persists independently of the selected application.
- **Application** — owned by one app and reclaimed on successful exit.
- **Mode/operation** — optionally nested beneath an app for buffers that can be released before app exit, such as Recorder monitor FFT scratch or a temporary capture-processing workspace.
- **DMA/internal constrained** — tracked/documented where useful but allocated from the memory class required by ESP-IDF/peripheral hardware rather than blindly redirected to PSRAM.

The first implementation does not need a general-purpose replacement for `malloc()`. A small explicit API with owner-aware allocate/grow/free/release-all operations is preferable to allocator magic that makes ownership difficult to audit.

### Required behavior

- Prefer PSRAM for eligible large/growable app allocations.
- Support safe capacity growth with overflow checks and failure preserving the old allocation.
- Track owner, size, and enough metadata to release all allocations for one app.
- Make double-free, wrong-owner free, and release-after-worker-use diagnosable during development where practical.
- Treat missing/unusable PSRAM as an unsupported target/platform condition rather than silently shrinking the application model into internal SRAM.
- Expose current and peak usage per active app plus allocation-failure counters.
- Avoid unbounded metadata overhead or one allocator record per tiny transient object when a growable app container would be more appropriate.

### Memory-pressure policy

Dynamic growth is not equivalent to infinite storage. Each app must define what happens when a requested growth cannot be satisfied.

Preferred order:

1. Preserve correctness and currently displayed/currently processed data.
2. Release optional scratch/cached data that can be reconstructed.
3. Evict oldest/lowest-value retained history when the feature semantics allow it.
4. Surface a resource-pressure indication/counter.
5. Continue operating in a bounded state.

A crash, silent memory overwrite, or undocumented conversion of a `Never` retention setting into a small fixed limit is not acceptable degradation.

## Workstream B: lifecycle integration

### Transition contract

App changes are transactional until the final safety gate passes. Any operation before that gate that can fail must either be reversible or have an explicit reactivation path; destructive exit cleanup is not allowed to leave the source app half-torn-down when a transition is aborted.

On a requested app change:

1. Request quiesce from the current app.
2. Wait for bounded worker/peripheral shutdown.
3. If quiesce fails, abort the transition and reactivate the source app without reclaiming app memory.
4. Cancel/drain callbacks and timers that can reference app-owned state. Registrations or execution paths changed here must be restorable if the transition later aborts.
5. Run only reversible pre-exit preparation needed to make reachability testable. Do not discard histories/menu state, free app-owned storage, or perform other irreversible app-specific exit cleanup yet.
6. Verify that no worker, callback, timer, DMA completion path, or other execution context can still reference app-owned state. If this safety gate fails, abort the transition, restore any callback/timer registrations or peripheral/worker state changed during preparation, and reactivate the source app with its allocations and operational state intact.
7. Commit app-specific exit cleanup. All fallible work that could require rollback must already have completed; this commit phase must not recreate references to app-owned state and must not depend on a later fallible safety check.
8. Release all remaining memory owned by the exiting app.
9. Verify allocator/accounting state reports zero remaining allocations for the exited app.
10. Record transition/reclamation diagnostics.
11. Enter the destination app and use the existing settle/activation model.

This ordering is mandatory. The safety/reachability gate must happen before irreversible cleanup and reclamation; a post-free check is too late to prevent a race from becoming a use-after-free, and merely keeping allocations intact is not sufficient if the source app has already been destructively torn down. Post-reclamation verification is limited to allocator/accounting invariants such as confirming that no app-owned allocations remain.

The lifecycle API should therefore make the prepare/commit boundary explicit rather than treating today's `leave_app()` behavior as a single indivisible exit hook. Existing app-specific cleanup that resets histories, menus, or other runtime state belongs in the committed-exit phase unless it is redesigned with a defined rollback operation.

### Stress validation

Automate or manually exercise:

- rapid forward/backward rotation through every enabled app;
- repeated Home -> app -> Home cycles;
- switching while WiFi/BLE collections are large;
- switching while CC1101/nRF24 history is large;
- Recorder monitor/record/playback transitions followed by immediate app exit;
- Thermal attach/detach and exit while active;
- failed/bounded quiesce paths;
- callback/timer cancellation races where practical;
- forced pre-reclamation safety-gate failure followed by continued use of the source app;
- low-memory injection or constrained-memory builds where practical.

Pass criteria include stable baseline free memory after repeated cycles, no falling largest-free-block trend attributable to leaked app allocations, zero app-owned allocations after successful exit, no stale worker/callback access, and a source app that is fully operational after any pre-commit transition abort.

## Workstream C: WiFi / BT retention semantics

### User choices

Represent retention as semantic choices rather than encoding special behavior as unexplained numeric sentinels in the UI:

- **Instant**
- finite timed values (retain the useful existing range unless implementation review changes it deliberately)
- **Never**

Configuration serialization may use a tagged/string representation or a carefully documented numeric representation, but schema migration must remain explicit and backward compatible.

### Meaning

**Instant** means an observation has no deliberate historical grace period. Housekeeping may remove it as soon as it is no longer current under the collector's normal observation rules. It does not disable scanning or notifications.

**Timed** means the observation remains eligible for display/history for the selected interval after last relevant observation, preserving independent Wi-Fi/BLE source aging for merged records.

**Never** disables age-based removal for the active WiFi / BT session. It does not persist observations to SD and does not survive leaving the app. Exiting WiFi / BT releases the collection along with all other app-owned runtime memory.

### Growth and pressure

Collections should grow geometrically or in sensible chunks rather than reallocating for every observation. When growth fails, use an explicit eviction/degradation policy and expose memory pressure. `Never` should attempt to retain all observations for the session within available resources, not reserve all PSRAM up front.

## Workstream E: visual theme and audio-policy separation

Theme and sound policy are independent user concerns and should not remain coupled through the current Discipline theme behavior.

### Planned user model

Visual themes should describe presentation only:

- **Indoor** — normal RFScout visual presentation.
- **Outdoor** — daylight/high-contrast visual presentation.
- **Night** — red/orange low-light visual presentation.

Audio policy should be a separate persistent setting:

- **Normal** — incidental UI feedback and enabled detection notifications are permitted, subject to existing per-app notification controls, global notification mode/volume, independent audio gain settings, and application-specific audio rules. Normal is an enablement policy, not a promise that every sound is rendered at 100% gain.
- **Quiet** — suppress incidental interaction/event sounds and detection-notification presentation while preserving explicitly requested application content audio.

This permits combinations such as Outdoor + Quiet, Night + Normal, or Night + Quiet without forcing a visual change merely to reduce sound.

### Audio-policy boundaries

The implementation should preserve the distinction among three audio classes:

1. **Application content audio** — explicitly requested by the user, such as Recorder playback or future CW transmission through the speaker. Quiet does not suppress this class.
2. **Detection notifications** — app-owned detections presented through Tone/Morse according to the global notification mode/volume and per-app notification controls. Quiet suppresses their audible presentation without changing the saved notification configuration.
3. **Incidental UI feedback** — navigation, activation, lock/unlock, warnings, and similar event feedback. Quiet suppresses ordinary incidental sound presentation; visual/state behavior remains unchanged.

The audio policy belongs in the feedback/notification policy layer rather than in the theme palette or visual theme resolver. Themes must not participate in deciding whether a sound is emitted or what gain is applied. Any environmental interaction/notification gain retained for compatibility must become independent audio state rather than remain an implicit property of the visual theme.

### Discipline migration

The standalone **Discipline** theme should be retired as part of the 0.4.0 configuration migration rather than retained indefinitely as a coupled theme/audio mode.

Migration requirements:

- A saved Discipline selection from an older configuration maps to **Night + Quiet** and materializes the Night environmental gain profile in the new independent audio state: `20%` interaction / `60%` notification. Quiet keeps the migrated device silent immediately after upgrade; if the user later deliberately selects Normal, it therefore behaves like Night rather than inheriting an ambiguous or permanently silent `0%` / `0%` profile.
- Existing Indoor, Outdoor, and Night configurations retain their visual selection and migrate to **Normal** audio policy while preserving their current effective theme-owned sound gains in new theme-independent audio state: Indoor `35%` interaction / `100%` notification, Outdoor `55%` / `100%`, and Night `20%` / `60%`.
- The migration must preserve the user's existing global notification volume semantics; the legacy notification percentage above is an environmental gain applied independently rather than silently replacing the user's configured global volume.
- New/default configurations may use the Indoor-equivalent gain values unless the implementation deliberately introduces explicit user-facing controls, but migration of existing configurations must not cause an audible level jump merely because visual and audio policy were separated.
- Saving after migration writes only the new independent theme/audio-policy/audio-gain fields; obsolete Discipline theme-owned sound state should not be re-emitted.
- Migration must preserve newer-schema rejection and the existing canonical configuration rewrite rules.

- [ ] Make Normal/Quiet a simple direct-cycle choice under the semantic menu policy.

## Workstream F: documentation consolidation

During implementation, keep documentation roles strict:

- `README.md`, `CAPABILITIES.md`, `ARCHITECTURE.md`, `CONFIGURATION.md`, and `APP_LIFECYCLE.md` describe current implemented behavior only.
- `ROADMAP.md` owns release scope, priorities, and future intent.
- This file owns the detailed v0.4.0 implementation checklist while the milestone is active.
- Once a workstream is implemented, move its factual contract into the appropriate production document and mark/remove completed planning details here rather than maintaining two competing descriptions.

At release-candidate time, perform a documentation pass for stale limits, fixed-capacity descriptions, old timeout ranges, Discipline/theme-coupled audio descriptions, and any statement that implies an app keeps runtime history after exit.
