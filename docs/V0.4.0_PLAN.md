# RFScout v0.4.0 implementation plan

This document is the detailed implementation checklist for the v0.4.0 roadmap milestone. It is intentionally forward-looking. Nothing here should be read as implemented behavior until the corresponding code is merged and the production documentation is updated.

The canonical release scope and rationale remain in [ROADMAP.md](ROADMAP.md). This file exists to keep the implementation sequence, ownership rules, and validation checklist together instead of spreading v0.4.0 planning across production documents.

## Release objective

Make RFScout applications behave like isolated consumers of a common pool of dynamic memory:

- long-lived platform services keep only the memory they genuinely need across applications;
- the active application may dynamically consume available PSRAM for retained observations, history, captures, and scratch processing;
- application exit first quiesces hardware/workers, proves that no execution context can still reference app-owned state, and only then releases all app-owned dynamic memory;
- the next application starts from a predictable memory baseline and can reuse the released PSRAM;
- PSRAM is a platform requirement for supported RFScout hardware targets.

This is resource isolation by lifecycle, not a promise that literally every byte of physical PSRAM is available to an application. Platform, RTOS, display, driver, DMA, and service allocations that must remain resident are excluded from the app-owned pool. Internal SRAM remains reserved for the system, stacks, latency-sensitive state, and allocations constrained by ESP-IDF or peripheral hardware.

## Workstream A: memory manager

### Ownership model

Define allocation ownership at minimum as:

- **Platform/service** — persists independently of the selected application.
- **Application** — owned by one app and reclaimed on successful exit.
- **Mode/operation** — optionally nested beneath an app for buffers that can be released before app exit.
- **DMA/internal constrained** — tracked/documented where useful but allocated from the memory class required by ESP-IDF/peripheral hardware.

Prefer a small explicit owner-aware allocate/grow/free/release-all API over allocator magic.

### Required behavior

- Prefer PSRAM for eligible large/growable app allocations.
- Support safe capacity growth with overflow checks and failure preserving the old allocation.
- Track owner, size, and enough metadata to release all allocations for one app.
- Make ownership errors diagnosable during development where practical.
- Treat missing/unusable PSRAM as an unsupported target condition rather than silently substituting internal SRAM.
- Expose current/peak usage per active app plus allocation-failure counters.
- Avoid excessive metadata overhead for tiny transient objects.

### Memory-pressure policy

Preferred order when growth fails:

1. Preserve correctness and current data.
2. Release reconstructable scratch/cache data.
3. Evict oldest/lowest-value retained history where semantics permit.
4. Surface resource pressure.
5. Continue in a bounded state.

A crash, overwrite, or undocumented conversion of `Never` into a small fixed limit is not acceptable.

## Workstream B: lifecycle integration

### Transition contract

App changes are transactional until the final safety gate passes. Before that gate, fallible operations must be reversible or have an explicit reactivation path.

1. Request quiesce from the current app.
2. Wait for bounded worker/peripheral shutdown.
3. On failure, abort and reactivate the source app without reclaiming memory.
4. Cancel/drain callbacks and timers that can reference app-owned state, reversibly where necessary.
5. Perform only reversible pre-exit preparation.
6. Verify no worker, callback, timer, DMA completion path, or other execution context can reference app-owned state; on failure restore/reactivate.
7. Commit irreversible app-specific exit cleanup only after the final fallible gate.
8. Release remaining app-owned memory.
9. Verify zero remaining allocations for the exited app.
10. Record diagnostics.
11. Enter the destination app using the existing settle/activation model.

The lifecycle API should make the prepare/commit boundary explicit. Post-reclamation checks verify allocator/accounting invariants, not reachability that should have been proven before freeing memory.

### Stress validation

Exercise rapid app rotation, repeated Home/app cycles, large WiFi/BLE and RF histories, Recorder transitions, Thermal attach/detach, failed quiesce and reachability gates, callback/timer races, and low-memory conditions. Pass criteria include stable baseline memory, no systematic largest-free-block decline, zero app allocations after successful exit, no stale accesses, and full source-app recovery after an aborted transition.

## Workstream C: WiFi/BLE retention and observation semantics

Rename the user-facing **WiFi / BT** application to **WiFi / BLE** in v0.4.0. RFScout currently observes Bluetooth Low Energy rather than generic/classic Bluetooth, and the more precise name becomes increasingly important as BLE-specific analysis is exposed.

### User choices

Represent retention as semantic choices:

- **Instant**
- finite timed values
- **Never**

Configuration serialization may use tagged/string or carefully documented numeric representation, but migration must remain explicit and backward compatible.

### Meaning

**Instant** gives an observation no deliberate historical grace period. It does not disable scanning or notifications.

**Timed** keeps observations/history eligible for the selected interval after their last relevant evidence. Wi-Fi and BLE source aging remains independent where a higher-level entity has evidence from both radios.

**Never** disables age-based removal for the active WiFi/BLE session. It does not persist observations to SD and does not survive leaving the app; app exit releases the collection.

Timeouts define whether evidence is **current**, not whether an object must immediately vanish from an interactive drill-down. A selected/deep-dive object may transition from active to stale and remain temporarily inspectable while referenced by the UI/history. Once unreferenced, normal retention and memory-pressure reclamation apply. Live lists should avoid cursor-destabilizing disappearance/reordering while the user is navigating them.

### Growth and pressure

Collections should grow geometrically or in sensible chunks. `Never` attempts to retain all session observations within available resources rather than reserving all PSRAM up front. Memory pressure may preferentially discard stale, low-confidence, or low-value transient observations before current/high-confidence entities, with visible diagnostics where useful.

### Identity model

Stop equating every observed MAC address with a physical device. Introduce stable app-internal entity IDs and retain the relationship between an entity, its observed radio identities/addresses, and the evidence used to associate them.

- Preserve raw observed addresses and address privacy/randomization state for inspection.
- Treat identity association as evidence/confidence, not proof of a persistent physical identity.
- Never merge stable/associated identities solely because device fingerprints look similar.
- Allow multiple randomized identities to be represented as one short-lived entity/scan-session cluster only when timing, sequence behavior, capabilities, RSSI/channel behavior, and other evidence are sufficiently compatible.
- Do not claim persistent correlation across independently randomized Wi-Fi associations or BLE private-address rotations when passive evidence cannot support it.
- Distinguish **protocol relationships** (for example Wi-Fi client -> AP) from **identity relationships** (multiple observed addresses likely representing one entity).

### Wi-Fi semantic observations

Replace the current MAC-only reduction with richer semantic 802.11 observations where practical. Preserve frame type/subtype, transmitter/receiver/BSSID roles, sequence information, channel/RSSI, SSID and relevant capability IEs, and association-strength evidence needed by the resolver.

Classify Wi-Fi evidence by confidence rather than treating all transmitters equally. Probe-only randomized identities are weak/transient evidence; authentication/association/reassociation exchanges, ordinary associated data traffic, and observed EAPOL/handshake traffic provide progressively stronger topology evidence. Handshake capture is useful confirmation but must not be required to discover an associated client.

Randomized Probe Requests remain valuable and must not simply be discarded. They should primarily feed ephemeral unassociated-client/scan-session clustering and probe analysis rather than inflating the primary device count. Requested SSIDs are relationship/history data, not identity keys.

### Wi-Fi views and relationships

Provide radio-specific main views, with a compact `View` setting suitable for direct cycling where practical:

- **SSIDs** — group observations by the advertised/requested SSID label for analysis only. An SSID is not a unique network identity: unrelated APs can advertise the same name, so the grouping must preserve individual BSSIDs and must not imply that same-named APs share topology, administration, or clients unless separate observed evidence supports that relationship.
- **APs** — access points/BSSIDs only.
- **Clients** — associated or otherwise strongly evidenced client entities.
- **Unassociated** — lower-confidence/probe-only transient client clusters; clearly lower priority than associated clients.
- **Probes** — aggregate requested SSID labels and show which transient/client entities are requesting them, including broadcast/wildcard probes where observable.

Deep-dive navigation should permit AP -> associated clients, SSID label -> APs advertising that label plus clients/probes linked to each AP or request observation without flattening them into one inferred network, client -> associated AP and probe history, and probed SSID -> requesting clients/clusters. Lists remain live while open but preserve stable selection through internal IDs and active/stale state.

### BLE views and relationships

Do not force Wi-Fi AP/probe terminology onto BLE. BLE has different passive semantics and should expose views that reflect what RFScout can actually infer:

- **Devices** — de-duplicated/entity-centric BLE observations where identity correlation has adequate evidence.
- **Advertisers** — advertisement-centric/rawer RF view preserving observed addresses and advertisement activity.
- **Beacons** — recognized beacon/manufacturer-specific advertising such as supported iBeacon/Eddystone-style or other identifiable formats.
- **Services/Capabilities** — advertised service UUIDs, manufacturer data, names, appearance/capability metadata, and other useful advertisement-derived information.

BLE address privacy/randomization should use the same general entity -> observed identities architecture as Wi-Fi but radio-specific correlation evidence. Do not present a BLE AP equivalent. Do not claim established BLE central/peripheral connections merely from ordinary advertisement scanning; expose protocol-level BLE connection relationships only if a future collector can reliably observe/follow them. Identity associations among rotating BLE addresses may still be shown with confidence/provenance.

### Main and deep-dive UI

Make radio type a first-class view dimension rather than mixing incompatible Wi-Fi and BLE concepts:

- **Radio: Combined / Wi-Fi / BLE**
- **Combined** retains a useful nearby/surveillance overview without pretending all entities share the same topology.
- **Wi-Fi** unlocks SSIDs/APs/Clients/Unassociated/Probes views.
- **BLE** unlocks Devices/Advertisers/Beacons/Services views.

The main screen remains an actively updated analytical projection. Use menus for deeper relationship exploration rather than overloading rotary scrolling with row-selection semantics. Context-sensitive detail menus should expose only relationships supported by the selected entity and radio.

## Workstream E: visual theme and audio-policy separation

**Implementation status:** Implemented by PR #60. The code and production-documentation changes in this PR establish the independent visual/audio policy model, schema-v3 migration, and downgrade-safe recovery described below. Release-level verification remains tracked in the unchecked validation items and release checklist until CI/device testing is complete.

Visual themes describe presentation only: **Indoor**, **Outdoor**, and **Night**. Audio policy is a separate persistent **Normal** or **Quiet** setting. Quiet suppresses incidental UI feedback and audible detection notifications without mutating saved notification configuration, but does not suppress explicitly requested content audio such as Recorder playback.

The standalone **Discipline** theme is retired through schema-v2 -> schema-v3 migration. Discipline maps to Night + Quiet with `20%` interaction / `60%` notification environmental gains. Indoor, Outdoor, and Night migrate to Normal while preserving effective legacy gains: Indoor `35%`/`100%`, Outdoor `55%`/`100%`, Night `20%`/`60%`. Global notification-volume semantics remain independent.

Downgrade safety preserves and recovers a validated schema-v3 configuration when schema-v2 firmware quarantines the newer document and writes defaults. Recovery does not resurrect corrupt or unrelated quarantine files. Saving after migration emits only canonical schema-v3 independent theme/audio-policy/audio-gain state.

## Release validation checklist

- [ ] All tests/build/format checks pass.
- [ ] App-switch stress testing shows stable baseline memory, no ownership violations, and zero app-owned allocations after successful exit.
- [ ] Pre-reclamation safety gates prove no worker/callback/timer can reference app memory; forced failures fully restore the source app before irreversible cleanup.
- [ ] Largest free block remains stable enough to rule out systematic fragmentation/leak growth.
- [ ] WiFi/BLE Instant, finite timed, and Never behavior is verified, including full reclamation on exit and memory-pressure paths.
- [ ] Wi-Fi primary device counts are not inflated one-for-one by rotating randomized Probe Request MACs.
- [ ] Wi-Fi AP/client topology and probe relationships are derived from appropriate 802.11 evidence, handshake observation is not required for ordinary associated-client discovery, and SSID groupings are treated only as non-unique labels unless separate evidence supports a stronger relationship.
- [ ] Unassociated/probe-only identities are clearly lower-confidence/transient and conservative clustering does not merge unrelated stable clients.
- [ ] Combined/Wi-Fi/BLE main views and context-sensitive deep dives remain actively updated without destabilizing user selection when entries become stale.
- [ ] BLE views use BLE-native advertiser/device/beacon/service semantics and do not claim AP-like hierarchy or unobserved connections.
- [ ] Rotating Wi-Fi/BLE addresses preserve raw identity/provenance and any entity correlation is represented as evidence rather than guaranteed physical identity.
- [ ] Supported hardware provides usable PSRAM and fails clearly when the platform requirement is unmet.
- [ ] Recorder DMA/internal-memory requirements remain in compatible memory and audio controls use documented percentage-versus-dB semantics.
- [ ] Thermal absolute temperature/range/min/max/center presentation is gated on calibrated MLX90640 conversion and validated against hardware reference measurements; raw IR codes are never mislabeled as temperatures.
- [ ] Shared capability/status presentation derives from semantic application availability.
- [ ] Theme selection and Normal/Quiet audio policy operate independently; schema migration/downgrade recovery and legacy gains are verified.
